1. Introduction

Web application security is a growing concern in modern software development. Many common vulnerabilities — including Cross-Site Scripting (XSS), clickjacking, and man-in-the-middle attacks — can be significantly mitigated through the correct configuration of HTTP security response headers. Yet misconfigured or missing headers remain one of the most frequently observed weaknesses in real-world web applications.

This project implements an Automated Web Security Scanner: an interactive tool that allows a developer or security professional to assess the HTTP security posture of a web server they own or control. The tool performs entirely passive, non-intrusive checks — it reads response headers and reports findings with severity ratings and remediation guidance, without sending any attack payloads or attempting to exploit vulnerabilities.

Ethical Use Statement: This tool is designed exclusively for use against websites the operator owns or has explicit written permission to assess. Scanning third-party websites without permission may be illegal and is strictly outside the intended scope of this project.

2. Objectives

  • Build a single-file Python application (app.py) covering both scanner logic and dashboard UI
  • Perform passive HTTP security header checks against a user-supplied URL
  • Detect missing or misconfigured security headers: CSP, HSTS, X-Content-Type-Options, X-Frame-Options
  • Perform a basic CORS configuration check by reading the Access-Control-Allow-Origin header
  • Classify each finding with a severity level (High / Medium / Pass)
  • Provide clear explanations and actionable remediation advice for each finding
  • Implement robust input validation and error handling (timeouts, SSL errors, connection failures)
  • Present results through a professional, user-friendly Streamlit dashboard

5. Implemented Security Checks

5.1 HTTPS Usage

Inspects the URL scheme using urllib.parse.urlparse(). If the scheme is http, the finding is rated High — plain HTTP traffic is unencrypted and susceptible to man-in-the-middle (MITM) interception. No network request is required for this check.

5.2 Content-Security-Policy (CSP)

Checks for the presence of the Content-Security-Policy response header. CSP allows a server to declare trusted content sources, significantly reducing the attack surface for Cross-Site Scripting (XSS) and data-injection attacks. Absence is rated High.

5.3 Strict-Transport-Security (HSTS)

Checks for the Strict-Transport-Security header. HSTS instructs browsers to communicate with the site exclusively over HTTPS, preventing SSL-stripping attacks and accidental HTTP connections. Absence is rated High.

5.4 X-Content-Type-Options

Checks for the X-Content-Type-Options: nosniff header. Without it, some browsers perform MIME-type sniffing, which can allow an attacker to cause a text file to be interpreted as JavaScript. Absence is rated Medium.

5.5 X-Frame-Options

Checks for the X-Frame-Options header, which prevents the page from being embedded in an <iframe> on a different domain. Its absence makes the site vulnerable to clickjacking, where an attacker layers an invisible frame over a legitimate page to hijack user clicks. Absence is rated Medium.

5.6 CORS Configuration

Passively reads the Access-Control-Allow-Origin (ACAO) header. If the value is * (wildcard), the finding is rated Medium — any third-party website can read responses from this endpoint, which is a risk if the endpoint ever returns user-specific data. A specific origin value or absence of the header both receive a Pass.

6. Input Validation & Error Handling

6.1 Input Validation

Before any network call is made, validate_url() uses urllib.parse.urlparse() to verify:

  • The URL is non-empty
  • The scheme is strictly http or https
  • A valid hostname (netloc) is present

Invalid input is rejected with a descriptive error message rendered via st.error(), and execution halts with st.stop().

6.2 Network Error Handling

The fetch_response() function wraps requests.get() in a try/except block covering four exception classes:

ExceptionCauseUser-facing Message
requests.exceptions.Timeout Server did not respond within 10 seconds Timeout message with the configured timeout value
requests.exceptions.SSLError Invalid or expired TLS certificate SSL error with the exception detail
requests.exceptions.ConnectionError DNS failure, refused connection, or network unreachable Connection error with the exception detail
requests.exceptions.RequestException Any other requests-level failure Generic request failure message

On error, a High finding is added to the results list instead of raising an unhandled exception. The user sees a clear message within the normal scan results UI.

7. Dashboard Design

The Streamlit dashboard is structured into five areas:

AreaComponentPurpose
Header st.title, st.caption Project title and ethical-use disclaimer
Sidebar st.text_input, st.button URL entry, scan trigger, checks list, ethical-use warning
Pre-scan Info st.columns, st.markdown Tool description, severity legend, usage instructions
Results st.metric, st.expander Summary counts (total / pass / warn / fail) + per-finding cards
Footer st.caption Responsible-use reminder

Finding cards are ordered by severity — failures first, then warnings, then passes. FAIL and WARN cards are auto-expanded so the most important issues are immediately visible. Each card contains a Finding block (what was detected and why it matters) and, for non-passing results, a Remediation block with a concrete fix.

8. Data Flow

The following describes the end-to-end data flow for a single scan:

  1. User enters a URL and clicks Run Scan
  2. validate_url() checks scheme and hostname — halts on invalid input
  3. check_https() evaluates the scheme without a network call
  4. fetch_response() issues one GET request with a 10-second timeout
  5. On success, check_security_headers() iterates over the four required headers
  6. check_cors() reads the ACAO header value
  7. run_scan() assembles all findings into a flat list of dicts
  8. The dashboard counts severities, renders metrics, sorts findings, and displays expander cards

9. Finding Data Model

11. Limitations

  • Header presence only: The tool checks for the existence of headers, not the correctness of their values (e.g., it does not validate whether a CSP policy is restrictive or overly permissive)
  • Single endpoint: Headers are checked on the single URL provided. Other pages or API endpoints on the same server may have different header configurations
  • No authentication: The scanner makes unauthenticated requests; headers that only apply behind a login are not assessed
  • No active testing: By design, no payloads are injected and no active exploitation attempts are made — this is a feature, not a gap, given the passive-only requirement
  • Firewall sensitivity: Some servers may block or alter responses to requests from automated user agents

12. Potential Future Improvements

  • CSP policy strength analysis (e.g., detecting unsafe-inline or unsafe-eval directives)
  • HSTS max-age value validation (e.g., flagging values below the recommended 31,536,000 seconds)
  • Cookie security attribute checks (Secure, HttpOnly, SameSite)
  • Referrer-Policy and Permissions-Policy header checks
  • Exportable scan report (PDF or JSON download)
  • Multi-URL batch scanning

13. Conclusion

The Automated Web Security Scanner successfully meets all defined objectives. It provides a passive, safe, and user-friendly tool for identifying common HTTP security header misconfigurations. The application is built entirely within a single Python file, uses only two third-party libraries, and produces clear, actionable output that a developer can act on immediately.

The project demonstrates practical application of cybersecurity concepts — including transport security, content injection defences, framing attacks, and CORS — within a real, working tool. Its passive-only design ensures it can be used responsibly and legally on targets the operator controls.
